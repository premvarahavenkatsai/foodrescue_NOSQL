1. Introduction & Project Context

In urban centers, staggering quantities of nutritious, edible food are discarded daily by commercial kitchens, restaurants, wedding banquets, and university dining halls due to short shelf-life windows (3 to 10 hours for cooked foods) and the absence of structured redistribution channels. Concurrently, charitable shelters, orphanage pantries, and community kitchens struggle with daily ingredient shortages.

  • Project Goal: Match surplus food to nearby recipient shelters, enforce strict food safety validation via MongoDB $jsonSchema, dispatch volunteer couriers safely without race conditions, and predict claim success and delivery turnaround time using Scikit-Learn models.
  • Framing & Food Safety Disclaimer: FoodRescue enforces operational software verification workflows (recording holding temperatures, preparation hours, and packaging types) rather than certifying microbiological laboratory safety. All data is synthetically seeded (seed=42). Real-world food redistribution in India is guided by FSSAI surplus food regulations.
  • Stakeholders (users.role): Donors (list surplus food batches), Recipients/NGOs (claim batches), Volunteer Couriers (transport food), and Administrators (verify organizations and audit ML models).

  • Why MongoDB (NoSQL) Instead of SQL?: Each food category has distinct specs: cooked meals have holding temperatures and allergen arrays, bakery products have batch baking hours, and fresh produce has crate counts. In SQL, one table would have many empty NULL columns, or 6 separate tables would require complex JOINs. In MongoDB, each food batch embeds its own specs object cleanly in one document.

  • CAP Theorem Trade-off (CP): MongoDB replica sets choose CP (Consistency + Partition Tolerance). All writes target the primary node so two volunteers can never reserve the exact same food batch simultaneously on divergent partitions.
  • Single MongoClient Pool (backend/database/connection.py): get_client() creates one shared MongoClient from MONGO_URI in .env so PyMongo reuses socket connections instead of opening a new socket on every request.

Honest Limitation of $jsonSchema: MongoDB's $jsonSchema only checks static rules when a document is saved and cannot compare a field dynamically against the server's moving clock ($$NOW). Therefore, $jsonSchema checks that availableUntil is a valid BSON Date, while application queries check that availableUntil >= datetime.now() at search time.

6. Food Donation Lifecycle State Machine & Atomic Concurrency

Food redistribution follows a strict linear state transition lifecycle: available -> requested -> assigned -> picked_up -> delivered. Status transitions cannot skip intermediate inspection or courier handoff stages.

Atomic Compare-and-Swap in POST /api/deliveries/{id}/accept (Prevents Double-Reservation):

updated_task = db.delivery_tasks.find_one_and_update( filter={ "_id": ObjectId(task_id), "status": "pending_pickup", "volunteerId": None # Must still be unassigned! }, update={ "$set": { "status": "assigned", "volunteerId": ObjectId(current_user["id"]), "assignedAt": datetime.now(timezone.utc) } }, return_document=ReturnDocument.AFTER ) if updated_task is None: return jsonify({"error": "Concurrent modification detected / already claimed"}), 409

8. Machine Learning Data Preprocessing Pipeline

The ML data preprocessing pipeline transforms raw MongoDB records from foodrescue_db.ml_rescue_records into structured feature tensors:

  1. PyMongo Extraction: Training records are read directly via PyMongo (db.ml_rescue_records.find({}, {'_id': 0})) into a Pandas DataFrame.
  2. Categorical Encoding: OneHotEncoder(handle_unknown='ignore', sparse_output=False) converts foodCategory (6 classes), donorType (5 classes), and transportMode (4 classes) into 15 orthogonal binary columns.
  3. Mathematical Standardization: Continuous numerical variables (quantityKg, shelfLifeHours, distanceKm, storageTempCelsius, prepHour, isWeekend) are scaled to zero-mean and unit variance using StandardScaler: z = (x - μ) / σ.
  4. 80/20 Train/Test Partitioning: 1,200 training samples and 300 test holdout samples partitioned with stratify=y_clf to preserve exact class balance.

9. Machine Learning Model Implementations

A. Regression Models (Predicting Delivery Turnaround Minutes)

  • 1. Linear Regression: Fits Ordinary Least Squares (OLS) hyper-plane coefficients.
  • 2. Random Forest Regressor: 100 bagged regression trees capturing non-linear transit bottlenecks and peak-hour traffic windows.

B. Classification Models (Predicting Claim Success / Spoilage)

  • 3. Logistic Regression: Models the log-odds of claim success before expiry using the logistic sigmoid function.
  • 4. Decision Tree Classifier: Recursively partitions feature space using Gini impurity thresholds.
  • 5. Random Forest Classifier: Ensemble of 100 randomized decision trees voting to reduce classification variance.

12. End-to-End Workflow, Key Algorithms & Setup Steps

  • End-to-End Rescue Cycle: 1. Donor lists batch (POST /api/donations) -> 2. ML engine estimates claim likelihood and turnaround time -> 3. NGO reserves batch (POST /api/requests) -> 4. Courier accepts task atomically (POST /api/deliveries/{id}/accept) -> 5. Shelter confirms receipt -> 6. Courier earns gamified impact points idempotently.
  • Key Algorithms & Complexity: (1) State machine lookup in O(1) constant time; (2) Preprocessor feature transformations in O(N); (3) Random Forest inference in O(B * depth).
